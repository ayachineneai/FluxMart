# FluxMart 商品设计

## 1. 商品

### 说明

### 字段

| field | Java type      | Required | Business meaning | Constraint                           |
| --- |----------------| --- | --- |--------------------------------------|
| `productCode` | `ProductCode` | 是 | 商品业务编号 | 系统自动生成、全局唯一、创建后不可修改且不可复用             |
| `status` | `ProductStatus` | 是 | 商品状态 | 只能是 `DRAFT`、`ON_SALE`、`OFF_SALE` 或 `ARCHIVED`；新建商品默认为 `DRAFT` |
| `title` | `String`       | 是 | 商品标题 | 去除首尾空格后不能为空，长度不超过 50 个字符             |
| `subtitle` | `String`       | 否 | 商品副标题或简短卖点 | 有值时去除首尾空格，长度不超过 50 个字符               |
| `description` | `String`       | 是 | 商品详细描述 | 去除首尾空格后不能为空                          |
| `category` | `Category`     | 是 | 商品所属类目 | 创建商品或变更类目时，必须是当时有效的叶子类目；后续类目树变化不追溯使已有商品失效 |
| `primaryImageFileId` | `FileResourceId`       | 是 | 商品主图文件标识 | 不能为空；必须引用可用的文件资源 |
| `galleryImageFileIds` | `List<FileResourceId>` | 是 | 商品轮播图文件标识，可以为空列表 | 列表不能为 `null`；元素不能重复并保持展示顺序 |
| `specifications` | `List<Specification>` | 是 | 商品定义的销售规格 | 列表不能为 `null`，可以为空；规格编号和名称不能重复 |
| `skus` | `List<Sku>` | 是 | 商品包含的 SKU | 列表不能为 `null`；草稿编辑期间可以为空，发布时至少包含一个 SKU；SKU 编号和规格组合不能重复；无销售规格时必须且只能包含一个默认 SKU |

### 业务编号值对象

业务编号在领域层使用不同值类型，防止商品编号、SKU 编号和规格编号等底层都是字符串时被错误混用：

```java
public record ProductCode(String value) {}
public record CategoryCode(String value) {}
public record SkuCode(String value) {}
public record SpecificationCode(String value) {}
public record SpecificationValueCode(String value) {}
public record ReservationCode(String value) {}
public record OrderCode(String value) {}
```

数据库列和 JSON 仍然可以使用字符串，进入领域层时转换成对应值对象。

### 商品状态

| value | Business meaning |
| --- | --- |
| `DRAFT` | 商品正在编辑，不能被消费者查询或购买 |
| `ON_SALE` | 商品已上架，可以向消费者展示并参与下单判断 |
| `OFF_SALE` | 商品已下架，不能创建新订单，但历史订单继续保留 |
| `ARCHIVED` | 商品已永久归档，对消费者和商家日常列表不可见，不能重新上架，但历史数据继续保留 |

允许的主要状态变化：

```text
DRAFT -> ON_SALE
ON_SALE -> OFF_SALE
OFF_SALE -> ON_SALE
OFF_SALE -> ARCHIVED
```

`OFF_SALE` 是可逆的暂停销售，`ARCHIVED` 是不可逆的业务终态。正在销售的商品必须先下架，再归档。

状态变化必须通过具有业务含义的命令完成，不能开放通用的 `setStatus`：

```text
publish()
takeOffSale()
relist(context)
archive()
```

执行 `publish()` 时必须同时满足：

- 商品基础字段完整，目标类目及其整个祖先链均为 `ACTIVE`，并且目标类目是当时的叶子类目
- 至少存在一个 SKU，并且至少有一个 `ENABLED` SKU
- 每个 SKU 的价格大于零，规格选择完整、合法，商品内的规格组合不重复
- 无规格商品必须且只能有一个规格选择为空的默认 SKU
- 有规格商品的每个 SKU 必须对每个规格恰好选择一个 `ACTIVE` 规格值

允许零库存商品发布。发布只表达商品进入销售生命周期，缺货不等于下架。

`DRAFT` 商品可以通过应用服务命令 `discardDraftProduct(productCode)` 放弃，而不能由调用方直接执行普通 Repository 删除。前置条件是商品当前为 `DRAFT`，且不存在活动、审核、搜索索引或异常迁移数据等外部引用。正常业务中草稿不能下单，因此不应产生订单、库存预占或支付引用；如检测到这些异常引用，也必须拒绝删除。删除草稿时，其草稿 SKU、初始库存等从属数据必须在同一事务中清理；商品图片等外部资源可以通过后续清理任务回收。

商品归档不会删除数据。已经进入销售生命周期或产生外部业务引用的商品不能物理删除。即使草稿被物理删除，已经分配的 `productCode` 和 `skuCode` 也不能重新使用。

归档商品时不自动把所有 SKU 改为 `DISABLED`。商品状态和 SKU 状态表达不同事实：归档后的 SKU 即使仍为 `ENABLED` 也无法购买，但可以保留其归档前未被单独停用的历史语义。管理界面应展示派生的“可购买”结果，避免把 `ENABLED` 误解成当前可售。

## 2. 类目

### 说明

`Category` 表示商品所属的业务类目。类目具有自己的业务编号、名称和父级类目，可以被多个商品共同使用。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `categoryCode` | `CategoryCode` | 是 | 类目业务编号 | 系统自动生成、全局唯一、创建后不可修改且不可复用 |
| `name` | `String` | 是 | 类目名称 | 去除首尾空格后不能为空，长度不超过 50 个字符 |
| `status` | `CategoryStatus` | 是 | 类目状态 | 只能是 `ACTIVE`、`DISABLED` 或 `ARCHIVED` |
| `parentCategory` | `Category` | 否 | 父级类目 | 根类目为空；不能指向自身；类目关系中不能形成循环 |

### 类目状态

| value | Business meaning |
| --- | --- |
| `ACTIVE` | 允许新商品关联或已有商品主动变更至此类目 |
| `DISABLED` | 暂停接受新关联，已有商品继续保留原关联并可展示 |
| `ARCHIVED` | 从运营日常列表隐藏，不能接受新关联，历史关联继续保留 |

### 层级示例

```text
服装
└── 男装
    └── T 恤
```

对应关系：

```text
Category("CLOTHING", "服装", null)
Category("MENS_CLOTHING", "男装", CLOTHING)
Category("TSHIRT", "T 恤", MENS_CLOTHING)
```

创建商品或变更商品类目时，应关联到当时最具体的有效叶子类目，例如 `T 恤`，而不是 `服装` 或 `男装`。“有效”表示目标类目及其整个祖先链均为 `ACTIVE`；只要任一祖先为 `DISABLED` 或 `ARCHIVED`，就不能产生新的类目关联。

类目树后续可能发生变化。例如原来的叶子类目新增子类目后，它将不再是叶子类目。已有商品继续保留原类目关联，不会因此失效，也不影响标题、图片等其他字段的修改。只有新建商品或主动变更商品类目时，才校验目标类目在当前类目树中是否为叶子类目。

## 3. 规格

### 说明

`Specification` 表示消费者购买商品时需要选择的一个规格维度，例如颜色、尺码或容量。

规格属于商品，负责定义可以选择哪些值；SKU 负责记录自己在每个规格上选择了哪个值。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `specificationCode` | `SpecificationCode` | 是 | 规格业务编号 | 系统自动生成，在商品内唯一，创建后不可修改 |
| `name` | `String` | 是 | 规格名称 | 去除首尾空格后不能为空，在商品内不能重复 |
| `values` | `List<SpecificationValue>` | 是 | 规格允许选择的值 | 不能为 `null` 且至少包含一个值；规格值编号和展示名称不能重复 |

### 示例

```text
Specification
specificationCode = COLOR
name = 颜色
values = [BLACK/黑色, WHITE/白色]

Specification
specificationCode = SIZE
name = 尺码
values = [M/M, L/L]
```

商品没有颜色、尺码等销售规格时，`specifications` 使用空列表。发布时必须且只能包含一个默认 SKU，并且该 SKU 的 `specificationSelections` 必须为空；草稿编辑期间可以暂时没有 SKU。

## 4. 规格值

### 说明

`SpecificationValue` 表示一个规格允许选择的具体值，例如颜色规格下的“黑色”，或者尺码规格下的“M”。

规格值使用稳定的业务编号作为身份，展示名称可以修改。将“黑色”改名为“曜石黑”时，`specificationValueCode` 仍然是 `BLACK`，因此引用它的 SKU 规格组合不会变化。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `specificationValueCode` | `SpecificationValueCode` | 是 | 规格值业务编号 | 系统自动生成，在所属规格内唯一，创建后不可修改且不可复用 |
| `displayName` | `String` | 是 | 规格值展示名称 | 去除首尾空格后不能为空，在所属规格内不能重复 |
| `status` | `SpecificationValueStatus` | 是 | 规格值状态 | 只能是 `ACTIVE` 或 `RETIRED` |

`ACTIVE` 规格值允许用于创建新 SKU。`RETIRED` 表示规格值已经退役，不能再用于创建新 SKU，但已有 SKU 和历史订单仍可继续引用；是否停用已有 SKU 由商家单独决定，退役规格值不会自动停用相关 SKU。

### 示例

```text
SpecificationValue
specificationValueCode = BLACK
displayName = 黑色
```

修改展示名称：

```text
specificationValueCode = BLACK
displayName = 曜石黑
```

规格值编号没有变化，因此这属于展示名称修改，不会被识别成新的 SKU 组合。

## 5. 规格选择

### 说明

`SpecificationSelection` 表示一个 SKU 在某个规格上选择的规格值。它使用不同的编号值类型，编译器可以阻止规格编号和规格值编号传反。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `specificationCode` | `SpecificationCode` | 是 | 被选择的规格编号 | 必须是商品定义的有效规格 |
| `specificationValueCode` | `SpecificationValueCode` | 是 | 选择的规格值编号 | 必须属于对应规格 |

```java
public record SpecificationSelection(
        SpecificationCode specificationCode,
        SpecificationValueCode specificationValueCode
) {}
```

同一个 SKU 中不能重复选择同一个 `specificationCode`。

## 6. 金额

### 说明

`Money` 表示人民币金额。当前项目只支持人民币，因此领域模型不再保存币种。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `amount` | `BigDecimal` | 是 | 人民币元金额 | 不能小于零；最多两位小数 |

领域层使用 `Money`。持久化时可以将金额转换为最小货币单位的 `long`，例如人民币 `99.00` 元保存为 `9900` 分。

```java
public record Money(BigDecimal amount) {
    public Money {
        Objects.requireNonNull(amount);
        if (amount.signum() < 0) {
            throw new IllegalArgumentException("amount must not be negative");
        }
        amount = amount.setScale(2, RoundingMode.UNNECESSARY);
    }
}
```

非法精度应直接拒绝，不能静默舍入。例如 `99.001` 元是非法金额。通用 `Money` 可以为零；SKU 销售价格必须大于零，这是 SKU 自身的业务规则。持久化时只保存人民币分，例如 `99.00` 元保存为 `9900`。

## 7. SKU

### 说明

`Sku` 表示消费者实际购买的最小商品单元。同一个商品可以因为颜色、尺码或容量不同而包含多个 SKU。

价格属于 SKU，因为同一商品下的不同规格组合可以具有不同价格。实时库存由独立的 `Stock` 根据 `skuCode` 管理。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `skuCode` | `SkuCode` | 是 | SKU 稳定业务编号 | 系统自动生成、全局唯一、创建后不可修改且不可复用；不能由商家输入或编辑 |
| `merchantSkuCode` | `String` | 是 | 商家自定义 SKU 货号 | 由商家输入，可修改；去除首尾空格后不能为空，在商家范围内唯一 |
| `specificationSelections` | `List<SpecificationSelection>` | 是 | SKU 的规格选择 | 不能为 `null`；必须对商品的每个规格恰好选择一个有效值；规格不能重复选择；同一商品内规格组合不能重复 |
| `price` | `Money` | 是 | SKU 销售价格 | 人民币金额必须大于零 |
| `imageUrl` | `String` | 否 | SKU 专属图片 | 有值时必须是 `http` 或 `https` 绝对 URL，长度不超过 2048 |
| `status` | `SkuStatus` | 是 | SKU 可用状态 | 只能是 `ENABLED` 或 `DISABLED`；停用后不能创建新订单，但历史数据必须保留 |

### SKU 状态

| value | Business meaning |
| --- | --- |
| `ENABLED` | SKU 已启用，可以参与下单判断 |
| `DISABLED` | SKU 已停用，不能创建新订单，但历史订单、库存和统计数据继续保留 |

### 示例

商品“FluxMart 纯棉 T 恤”可以包含以下 SKU：

```text
SKU-001
merchantSkuCode = TSHIRT-BLACK-M
specificationSelections = [COLOR=BLACK, SIZE=M]
price = CNY 99.00

SKU-002
merchantSkuCode = TSHIRT-BLACK-L
specificationSelections = [COLOR=BLACK, SIZE=L]
price = CNY 99.00

SKU-003
merchantSkuCode = TSHIRT-WHITE-M
specificationSelections = [COLOR=WHITE, SIZE=M]
price = CNY 89.00
```

如果商品没有颜色、尺码等销售规格，发布时必须且只能存在一个默认 SKU：

```text
skuCode = SKU-DEFAULT-001
merchantSkuCode = CUP-001
specificationSelections = []
price = CNY 99.00
```

无规格商品不能创建第二个 `specificationSelections = []` 的 SKU。该规则需要直接校验，不依赖“规格组合不能重复”间接推导。

这样下单、计价和后续库存处理始终面向 SKU，不需要为“无规格商品”设计另一套流程。

### 领域身份与持久化身份

领域模型和系统间引用使用稳定的 `skuCode`。数据库持久化模型可以额外具有无业务含义的内部主键 `skuId`：

```text
领域模型：SkuCode
持久化模型：skuId + skuCode
```

库存、订单项等数据库外键可以关联内部 `skuId`；对外接口、业务日志和订单快照使用 `skuCode`。`merchantSkuCode` 只用于商家搜索、对货和运营管理，不能作为库存、订单或支付的稳定引用。数据库主键不进入当前业务字段表。

## 8. 商品规格与 SKU 变更规则

### 可以安全修改

- 商品标题、副标题、描述和图片
- 规格展示名称，但不能修改 `specificationCode`
- 规格值展示名称，但不能修改 `specificationValueCode`
- SKU 价格
- SKU 专属图片
- 商家自定义货号 `merchantSkuCode`，修改后仍需满足商家范围内唯一
- 新增规格值，并为新组合创建新 SKU

### 不允许直接修改

- 已存在 SKU 的 `skuCode`
- 已存在 SKU 的规格组合
- 已被 SKU 使用的 `specificationCode`
- 已被 SKU 使用的 `specificationValueCode`
- 已被 SKU 使用的规格或规格值不能物理删除

如果需要把 SKU 的规格组合从“黑色 / M”改成“黑色 / L”，必须：

```text
停用旧 SKU
创建具有新 skuCode 的新 SKU
```

不能直接修改旧 SKU 的规格组合，否则历史订单、库存、支付记录和统计数据的业务含义会被改变。

已被使用的规格不能物理删除。规格值不再提供时应将其设为 `RETIRED`，禁止新 SKU 使用，但不自动改变已有 SKU 的状态。尚未被任何 SKU 使用的规格或规格值可以直接删除。

### 商品可售判断

商品和 SKU 的状态相互独立。一个 SKU 允许创建订单，至少需要同时满足：

```text
Product.status == ON_SALE
Sku.status == ENABLED
Stock.availableQuantity >= requestedQuantity
```

其中前两个条件可以形成不包含库存的派生状态：

```java
boolean purchasable = product.status() == ON_SALE
        && sku.status() == ENABLED;
```

上架状态不等于库存状态。`availableQuantity = 0` 表示暂时缺货，不需要将商品下架或停用 SKU。缺货商品仍然可以展示，补货后可恢复下单。

## 9. 库存

### 说明

`Stock` 表示一个 SKU 当前的库存状态。库存按 SKU 管理，而不是按商品管理，因为同一商品下不同规格组合的库存不同。

库存与 SKU 基础信息分开建模。SKU 描述“卖什么、卖多少钱”，库存描述“现在还能卖多少”。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `skuCode` | `SkuCode` | 是 | 库存所属的 SKU 编号 | 必须对应一个有效 SKU；同一 SKU 只能有一份库存 |
| `availableQuantity` | `int` | 是 | 当前可以下单的数量 | 不能小于零 |
| `reservedQuantity` | `int` | 是 | 已被待支付订单锁定的数量 | 不能小于零 |
| `version` | `long` | 是 | 库存并发版本 | 初始值不能小于零；每次库存数量成功变化后递增 |

### 库存数量变化

库存数量不能由调用方直接加减。只有 `StockReservation` 成功发生状态转换后，才能产生对应的数量变化。

首次成功创建预占记录：

```text
availableQuantity -= quantity
reservedQuantity += quantity
```

预占记录从 `RESERVED` 转为 `CONFIRMED`：

```text
reservedQuantity -= quantity
```

此时商品已经正式售出，因此账面库存减少。`onHandQuantity` 不单独存储，可按下面的公式计算：

```text
onHandQuantity = availableQuantity + reservedQuantity
```

预占只是在支付确认前将数量从可售库存移动到锁定库存，只有确认后该数量才从账面库存消失。第一阶段库存只覆盖下单场景；未来增加采购入库、退货、盘点、报损或调拨时，应增加 `StockMovement`（库存流水），用 `INITIALIZE`、`INBOUND`、`RESERVE`、`RELEASE`、`SALE_CONFIRM`、`RETURN`、`ADJUSTMENT`、`DAMAGE` 等类型解释每次余额变化。

预占记录从 `RESERVED` 转为 `RELEASED`：

```text
reservedQuantity -= quantity
availableQuantity += quantity
```

所有库存操作都必须保证数量不会变成负数。预占库存时，如果 `availableQuantity < quantity`，则操作失败。

“数量不能为负”不能只依赖 Java 对象校验。多个请求可能同时读取同一个旧库存，因此数量变化必须由数据库原子更新或并发控制保证。

### 并发控制

使用 `version` 进行乐观锁更新：

```sql
UPDATE stock
SET available_quantity = available_quantity - :quantity,
    reserved_quantity = reserved_quantity + :quantity,
    version = version + 1
WHERE sku_id = :skuId
  AND available_quantity >= :quantity
  AND version = :version;
```

必须检查受影响行数：

```text
affectedRows == 1：库存预占成功
affectedRows == 0：SKU 不存在、库存不足或发生版本冲突，需要进一步判定
```

更新零行时必须重新读取：记录不存在则返回 SKU 不存在；最新可售库存不足才返回库存不足；否则判定为版本冲突并进行有限次数重试。不能把乐观锁冲突直接报告成库存不足，也不能忽略受影响行数并假设更新成功。

如果不使用乐观锁版本，也可以采用原子条件更新：

```sql
UPDATE stock
SET available_quantity = available_quantity - :quantity,
    reserved_quantity = reserved_quantity + :quantity
WHERE sku_id = :skuId
  AND available_quantity >= :quantity;
```

这种方案同样必须检查受影响行数是否为 `1`。FluxMart 当前模型保留 `version`，优先使用乐观锁方案。

### 示例

```text
Stock
skuCode = SKU-001
availableQuantity = 20
reservedQuantity = 3
version = 7
```

这表示 `SKU-001` 还有 20 件可以继续下单，另外 3 件已经被待支付订单锁定。

## 10. 库存预占

### 说明

`StockReservation` 记录某个订单对某个 SKU 的库存预占。它是库存操作实现幂等、追踪来源和处理超时释放的依据。

同一个订单与 SKU 的重复请求必须命中同一份预占记录，不能再次修改库存数量。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `reservationCode` | `ReservationCode` | 是 | 库存预占业务编号 | 系统自动生成、全局唯一、创建后不可修改且不可复用 |
| `orderCode` | `OrderCode` | 是 | 发起预占的订单编号 | 不能为空；与 `skuCode` 组成唯一业务键 |
| `skuCode` | `SkuCode` | 是 | 被预占的 SKU 编号 | 必须对应一个有效 SKU；与 `orderCode` 组成唯一业务键 |
| `quantity` | `int` | 是 | 本次预占数量 | 必须大于零，创建后不可修改 |
| `status` | `ReservationStatus` | 是 | 预占状态 | 只能是 `RESERVED`、`CONFIRMED` 或 `RELEASED` |
| `expiresAt` | `Instant` | 是 | 预占过期时间 | 必须晚于预占创建时间 |

如果一个订单中同一个 SKU 出现多次，应在创建订单时先合并数量，保证 `(orderCode, skuCode)` 只对应一份预占记录。

### 状态转换

```text
RESERVED -> CONFIRMED
RESERVED -> RELEASED
```

`CONFIRMED` 和 `RELEASED` 都是终态，二者之间不能互相转换。

### 幂等规则

| Operation | Current state | Result | Stock change |
| --- | --- | --- | --- |
| `reserve` | 记录不存在 | 创建 `RESERVED` | 可售减少，锁定增加 |
| `reserve` | `RESERVED` 且数量相同 | 直接返回成功 | 不变 |
| `reserve` | 已存在但数量不同 | 拒绝，返回幂等冲突 | 不变 |
| `confirm` | `RESERVED` | 转为 `CONFIRMED` | 锁定减少 |
| `confirm` | `CONFIRMED` | 直接返回成功 | 不变 |
| `confirm` | `RELEASED` | 拒绝 | 不变 |
| `release` | `RESERVED` | 转为 `RELEASED` | 锁定减少，可售增加 |
| `release` | `RELEASED` | 直接返回成功 | 不变 |
| `release` | `CONFIRMED` | 拒绝 | 不变 |

对应业务行为：

```text
reserve(orderCode, skuCode, quantity)
confirm(orderCode, skuCode)
release(orderCode, skuCode)
```

订单取消和预占超时都调用同一个 `release` 行为，复用相同的幂等规则。

### 整单原子预占

一个订单可能包含多个 SKU。FluxMart 第一阶段不允许部分预占成功，使用整单语义：

```text
reserveOrderStock(orderCode, items)
```

应用服务必须先合并相同 SKU 的数量，再按持久化 `skuId` 升序处理全部库存和预占记录，并在同一数据库事务中完成。任意 SKU 不存在、不可售或库存不足时，整笔事务回滚，不能留下部分成功的预占。统一处理顺序用于降低多 SKU 并发时的死锁概率。

### 超时释放与支付竞争

支付成功回调和超时释放可能同时尝试把 `RESERVED` 推向不同终态，状态条件更新必须确保只有一个转换成功。如果超时释放先完成，后到的支付确认不能把 `RELEASED` 改为 `CONFIRMED`。

第一阶段规定：订单超时后不再接受支付成功结果。若第三方仍然返回支付成功，则记录异常支付并发起原路退款，不能仅返回技术错误或在库存已经释放后继续履约。该补偿由订单域和支付域编排，库存域只提供可判定的终态。

### 并发约束

预占记录模型本身不能单独保证并发安全。实际持久化时必须同时保证：

- `(orderCode, skuCode)` 建立唯一约束
- 预占记录状态转换与 `Stock` 数量更新在同一事务中完成
- 状态更新带当前状态条件，例如只有 `RESERVED` 才能更新为 `RELEASED`
- 扣减可售库存时带 `availableQuantity >= quantity` 条件

这样两个并发的重复请求最多只有一个真正改变库存，其他请求读取已有预占结果并按幂等规则返回。

## 11. 订单商品快照

### 说明

创建订单时必须复制商品和 SKU 的关键数据，形成不可变的 `OrderItemSnapshot`。订单详情、退款和对账读取快照，不能依赖当前 `Product` 或 `Sku`。

订单项仍然保存 `productCode` 和 `skuCode` 用于问题追踪、统计和对账，但订单的标题、规格、图片和成交价格不通过这些编号实时查询。

### 字段

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `productCode` | `ProductCode` | 是 | 下单时的商品编号 | 创建快照后不可修改 |
| `skuCode` | `SkuCode` | 是 | 下单时的 SKU 编号 | 创建快照后不可修改 |
| `productTitle` | `String` | 是 | 下单时的商品标题 | 从商品复制，创建快照后不可修改 |
| `specificationSnapshot` | `List<SpecificationSnapshotItem>` | 是 | 下单时有序的规格身份与展示文本 | 从 SKU 和规格定义生成；按商品规格展示顺序保存，创建后不可修改 |
| `imageUrl` | `String` | 是 | 下单时展示的商品或 SKU 图片 | 优先使用 SKU 图片，否则使用商品主图 |
| `unitPrice` | `Money` | 是 | 下单时确认的 SKU 单价 | 不受商品后续改价影响 |
| `quantity` | `int` | 是 | 购买数量 | 必须大于零，创建快照后不可修改 |
| `totalAmount` | `Money` | 是 | 订单项总金额 | 必须等于 `unitPrice × quantity` |

### 规格快照项

```java
public record SpecificationSnapshotItem(
        SpecificationCode specificationCode,
        String specificationName,
        SpecificationValueCode specificationValueCode,
        String specificationValueName
) {}
```

```text
[
  { COLOR, 颜色, BLACK, 黑色 },
  { SIZE, 尺码, M, M }
]
```

快照同时保留下单时的展示文本、稳定业务编号和明确的展示顺序。名称供历史订单直接展示，编号用于对账和问题追踪；不能使用规格名称作为 `Map` 键，因为名称不是稳定身份，`Map` 类型也没有表达展示顺序。

### 快照规则

- 商品改名不改变历史订单标题
- 规格或规格值改名不改变历史订单展示
- SKU 改价不改变历史订单成交价
- 商品下架或归档不影响历史订单查询、退款和对账
- SKU 停用不影响历史订单
- 快照创建后不可修改；售后数据通过新的售后记录表达，不能回写历史快照

因此订单项不是对商品当前状态的实时投影，而是成交时商品事实的永久记录。

## 12. 聚合与加载边界

本文中 `Product.skus` 表达“商品由哪些 SKU 构成”的业务关系，不代表每次读取商品都必须把全部 SKU 作为一个无限增长的对象图加载。实际实现中：

- `Product` 管理商品内容、规格定义和商品生命周期
- `Sku` 通过 `productCode` 归属于商品，可以独立分页查询和持久化
- 新增或改变 SKU 时，由领域服务校验规格选择和组合唯一性
- 发布商品时，应用服务查询 SKU 的必要集合或校验摘要，构造 `ProductPublicationContext`，再执行 `product.publish(context)`
- 普通的商品标题修改、上下架等操作不加载库存，也不必加载全部 SKU 明细

这样仍然保留商品与 SKU 的领域规则，但不会让一个热门商品的 Product 聚合随着 SKU 数量不断膨胀。概念边界不要求拆成微服务；第一版可以继续使用同一个 Spring Boot 服务、Maven 模块和数据库。

## 13. 领域命令

领域模型不开放能够绕过不变量的通用 Setter。对外提供有业务语义的行为：

```text
Product:
changeTitle(title)
changeDescription(description)
changeCategory(category)
publish(context)
takeOffSale()
relist(context)
archive()

Sku:
changeMerchantSkuCode(merchantSkuCode)
changePrice(price)
changeImage(imageUrl)
enable()
disable()

StockReservation / Stock Repository:
reserve(orderCode, skuCode, quantity)
confirm(orderCode, skuCode)
release(orderCode, skuCode)
```

不允许暴露 `product.setStatus(...)`、`sku.setSpecificationSelections(...)` 或 `stock.setAvailableQuantity(...)`。库存对象中的行为可以用于表达规则和单线程领域测试，但生产环境的并发正确性最终必须由 Repository 的事务和原子 SQL 保证。

## 14. 数据库兜底约束

领域校验之外，数据库至少应提供以下唯一约束：

```text
UNIQUE(product_code)
UNIQUE(sku_code)
UNIQUE(merchant_id, merchant_sku_code)
UNIQUE(category_code)
UNIQUE(reservation_code)
UNIQUE(stock.sku_id)
UNIQUE(stock_reservation.order_id, stock_reservation.sku_id)
```

SKU 的规格选择先按 `specificationCode` 排序，生成不可依赖集合迭代顺序的规范化 `combinationKey`：

```text
COLOR=BLACK|SIZE=M
```

无规格 SKU 的组合键固定为 `DEFAULT`。数据库建立：

```text
UNIQUE(sku.product_id, sku.combination_key)
```

这可以在数据库层阻止同一商品出现重复规格组合，并保证无规格商品最多只有一个默认 SKU。领域层仍然显式校验“无规格商品必须且只能有一个默认 SKU”，以提供清晰的业务错误，而不是依赖唯一键异常间接表达规则。

图片 URL 的同步校验仅限于非空、长度以及 `http`/`https` 绝对地址。不在领域对象构造时发起网络请求，也不强制检查文件扩展名、Content-Type 或域名可访问性。若未来图片统一由自有对象存储管理，可以把 URL 替换为稳定的 `ImageResourceCode` 或对象键。

## 15. 领域边界

```text
商品目录域
├── Product / Category
├── Specification / SpecificationValue
├── Sku
└── Money

库存域
├── Stock
├── StockReservation
└── ReservationStatus

订单域
├── Order / OrderItem
└── OrderItemSnapshot
```

商品目录域负责商品内容、类目、销售规格、SKU 价格和销售生命周期；库存域负责余额、预占、确认、释放、并发和幂等；订单域负责购买数量、成交价格、商品快照和订单状态。跨域流程由应用服务编排，不能为了调用方便把库存余额重新塞回 SKU，或让历史订单实时读取当前商品信息。
