# FluxMart 商品操作设计

## 1. 操作边界

商品操作按业务意图拆分，不能用一个“保存商品”接口同时承担创建、编辑和状态变化。

| Operation | Meaning | State transition |
| --- | --- | --- |
| `mkProduct` | 创建商品草稿 | 不存在 → `DRAFT` |
| `editProduct` | 修改商品基础资料 | 状态不变 |
| `publishProduct` | 首次上架 | `DRAFT` → `ON_SALE` |
| `takeOffSaleProduct` | 下架 | `ON_SALE` → `OFF_SALE` |
| `relistProduct` | 重新上架 | `OFF_SALE` → `ON_SALE` |
| `archiveProduct` | 永久归档 | `OFF_SALE` → `ARCHIVED` |
| `discardDraftProduct` | 放弃未发布草稿 | `DRAFT` → 物理删除 |

每个操作都区分：

```text
用户输入：用户明确表达的业务意图
系统输入：系统查询或生成的权威事实，用于保证操作正确
输出：成功执行后返回的业务结果
副作用：为了取得系统输入或提交结果而发生的 IO 和状态变化
```

`productCode` 出现在编辑或状态操作的用户输入中，表示“用户要操作哪个商品”，但它不是可编辑的商品字段。

统一执行结构如下：

```text
读取或生成系统输入（有副作用）
        ↓
业务决策（用户输入 + 系统输入 → 输出，无 IO）
        ↓
提交输出（有副作用）
```

领域行为不能查询 Repository、生成编号或直接提交事务。应用服务负责执行这些副作用，并把获得的系统事实显式传给领域行为。

## 2. 创建商品

### 用户输入

```java
public record CreateProductInput(
        String title,
        String subtitle,
        String description,
        CategoryCode categoryCode,
        FileResourceId primaryImageFileId,
        List<FileResourceId> galleryImageFileIds
) {}
```

| field | Java type | Required | Business meaning | Constraint |
| --- | --- | --- | --- | --- |
| `title` | `String` | 是 | 商品标题 | 去除首尾空格后不能为空，长度不超过 50 个字符 |
| `subtitle` | `String` | 否 | 商品副标题 | 有值时去除首尾空格，长度不超过 50 个字符 |
| `description` | `String` | 是 | 商品详细描述 | 去除首尾空格后不能为空 |
| `categoryCode` | `CategoryCode` | 是 | 用户选择的类目 | 只是用户选择，系统仍需查询并验证真实类目 |
| `primaryImageFileId` | `FileResourceId` | 是 | 商品主图文件标识 | 必须引用可用的文件资源 |
| `galleryImageFileIds` | `List<FileResourceId>` | 是 | 商品轮播图文件标识 | 不能为 `null`，可以为空；不能重复并保持顺序 |

### 系统输入

```java
public record CreateProductSystemInput(
        ProductCode generatedProductCode
) {}
```

| field | Java type | Source | Correctness guarantee |
| --- | --- | --- | --- |
| `generatedProductCode` | `ProductCode` | 商品编号生成器 | 全局唯一、不可修改、不可复用 |

`categoryCode` 完整地属于用户输入。应用服务在调用纯函数前，根据它查询并校验类目：

```text
读取 input.categoryCode
查询 Category
确认类目真实存在、是有效叶子类目且祖先链均为 ACTIVE
校验通过后调用 createProduct
```

当前不再在系统输入中重复保存一份 `selectedCategoryCode`。以后如果创建商品需要使用类目的完整权威事实，可以传入 `Category`，但仍不应再复制一个来源相同的编号字段。

### 输出

```java
public record CreateProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

创建后的确定事实：

```text
productCode = generatedProductCode
status = DRAFT
specifications = []
skus = []
```

创建操作不会创建规格、SKU 或库存，也不会自动上架。

### 领域行为

```java
Product createProduct(
        CreateProductInput input,
        CreateProductSystemInput systemInput
);
```

领域行为输出一个新的 `Product`，应用服务持久化成功后向调用方返回 `CreateProductOutput(productCode, DRAFT)`。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 查询用户选择的真实类目及其祖先链 |
| 准备系统输入 | 从编号生成器取得新的 `productCode` |
| 提交输出 | 插入一条 `Product` 草稿记录 |
| 应用层控制 | 保存创建请求的幂等结果，防止重试产生重复商品 |

创建操作不写入规格、SKU 或库存表，也不产生上架状态变化。商品记录和幂等记录必须在同一个事务中提交。

## 3. 编辑商品基础资料

编辑操作只修改商品基础资料，不修改状态、规格、SKU、价格或库存。

### 用户输入

```java
public record EditProductInput(
        ProductCode productCode,
        String title,
        String subtitle,
        String description,
        CategoryCode categoryCode,
        FileResourceId primaryImageFileId,
        List<FileResourceId> galleryImageFileIds
) {}
```

字段约束与创建商品相同。这里采用完整替换语义：请求表达编辑完成后的整份基础资料，不使用 `null` 猜测某个字段是“不修改”还是“清空”。可空的 `subtitle` 可以显式传 `null` 清空。

### 系统输入

```java
public record EditProductSystemInput(
        Product currentProduct,
        Category selectedCategory
) {}
```

| field | Java type | Source | Correctness guarantee |
| --- | --- | --- | --- |
| `currentProduct` | `Product` | 根据 `productCode` 查询 | 商品存在，且不是 `ARCHIVED` |
| `selectedCategory` | `Category` | 根据 `categoryCode` 查询 | 如果类目发生变化，新类目必须是当前有效叶子类目 |

系统必须同时保证两个编号匹配：

```text
input.productCode == systemInput.currentProduct.productCode
input.categoryCode == systemInput.selectedCategory.categoryCode
```

### 状态规则

| Current state | Editable |
| --- | --- |
| `DRAFT` | 是 |
| `ON_SALE` | 是，修改后状态仍为 `ON_SALE` |
| `OFF_SALE` | 是 |
| `ARCHIVED` | 否 |

编辑不会隐式上架或下架。即使编辑后的商品已经满足发布条件，仍需显式执行 `publishProduct` 或 `relistProduct`。

### 领域行为

```java
Product editProduct(
        EditProductInput input,
        EditProductSystemInput systemInput
);
```

规格和 SKU 使用独立操作维护，例如 `defineSpecifications`、`createSku`、`changeSkuPrice` 和 `disableSku`，不属于 `editProduct`。

### 输出

```java
public record EditProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

输出中的状态与编辑前相同。输出只确认本次基础资料修改成功，不返回数据库主键。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 按 `productCode` 查询当前 Product |
| 准备系统输入 | 按 `categoryCode` 查询权威 Category；类目未改变时也可复用已加载事实 |
| 提交输出 | 更新商品标题、副标题、描述、类目和图片字段 |
| 并发控制 | 带当前版本更新 Product，成功后版本递增 |

编辑操作不更新商品状态，不写入规格、SKU 和库存，不触发自动上架或下架。

## 4. 首次上架

### 用户输入

```java
public record PublishProductInput(ProductCode productCode) {}
```

用户只表达“上架这个商品”，不能直接提交 `status = ON_SALE`。

### 系统输入

```java
public record ProductPublicationContext(
        Product currentProduct,
        Category currentCategory,
        List<SkuPublicationView> skus
) {}
```

| field | Java type | Source | Correctness guarantee |
| --- | --- | --- | --- |
| `currentProduct` | `Product` | 商品 Repository | 商品存在且当前为 `DRAFT` |
| `currentCategory` | `Category` | 类目 Repository | 类目及祖先链均为 `ACTIVE`，当前仍是叶子类目 |
| `skus` | `List<SkuPublicationView>` | SKU Repository | 属于该商品的完整发布校验数据，不要求 Product 聚合长期加载全部 SKU |

### 发布规则

- 商品基础字段完整
- 至少存在一个 SKU，且至少一个 SKU 为 `ENABLED`
- SKU 价格全部大于零
- SKU 规格选择完整、合法且组合不重复
- 无规格商品必须且只能有一个默认 SKU
- 有规格商品的每个 SKU 必须完整选择所有规格
- 可以零库存上架

### 领域行为

```java
Product publishProduct(
        PublishProductInput input,
        ProductPublicationContext context
);
```

成功后的唯一状态变化：

```text
DRAFT -> ON_SALE
```

### 输出

```java
public record PublishProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

成功时 `status` 固定为 `ON_SALE`。校验失败时没有成功输出，返回具体业务错误。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 查询当前 Product |
| 准备系统输入 | 重新查询当前 Category 及祖先链 |
| 准备系统输入 | 查询该商品用于发布校验的完整 SKU 数据 |
| 提交输出 | 将 Product 状态从 `DRAFT` 原子更新为 `ON_SALE`，并递增版本 |

首次上架不扣减库存、不创建订单，也不修改 SKU 状态。读取库存不是发布前置条件，因为零库存商品允许上架。

## 5. 下架

### 用户输入

```java
public record TakeOffSaleProductInput(ProductCode productCode) {}
```

### 系统输入

| System fact | Source | Required state |
| --- | --- | --- |
| 当前商品 | 商品 Repository | `ON_SALE` |

### 领域行为

```java
Product takeOffSaleProduct(
        TakeOffSaleProductInput input,
        Product currentProduct
);
```

成功后的唯一状态变化：

```text
ON_SALE -> OFF_SALE
```

下架不删除商品，不停用 SKU，也不释放已经存在的有效订单库存预占。它只阻止新的下单行为。

### 输出

```java
public record TakeOffSaleProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

成功时 `status` 固定为 `OFF_SALE`。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 按 `productCode` 查询当前 Product |
| 提交输出 | 将状态从 `ON_SALE` 原子更新为 `OFF_SALE`，并递增版本 |

没有 SKU 状态更新、库存释放或历史订单修改。

## 6. 重新上架

### 用户输入

```java
public record RelistProductInput(ProductCode productCode) {}
```

### 系统输入

重新上架使用与首次上架相同的 `ProductPublicationContext`，但当前商品状态必须为 `OFF_SALE`。因为商品下架期间类目、规格值或 SKU 可能已经变化，所以不能只修改状态，必须重新执行完整发布校验。

### 领域行为

```java
Product relistProduct(
        RelistProductInput input,
        ProductPublicationContext context
);
```

成功后的唯一状态变化：

```text
OFF_SALE -> ON_SALE
```

### 输出

```java
public record RelistProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

成功时 `status` 固定为 `ON_SALE`。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 查询当前 Product、当前 Category 及其祖先链 |
| 准备系统输入 | 查询该商品用于重新发布校验的完整 SKU 数据 |
| 提交输出 | 将状态从 `OFF_SALE` 原子更新为 `ON_SALE`，并递增版本 |

重新上架不修改 SKU 状态，也不要求或扣减库存。

## 7. 归档

### 用户输入

```java
public record ArchiveProductInput(ProductCode productCode) {}
```

### 系统输入

| System fact | Source | Required state |
| --- | --- | --- |
| 当前商品 | 商品 Repository | `OFF_SALE` |

### 领域行为

```java
Product archiveProduct(
        ArchiveProductInput input,
        Product currentProduct
);
```

成功后的唯一状态变化：

```text
OFF_SALE -> ARCHIVED
```

归档不可逆。归档不会删除历史数据，也不会自动把所有 SKU 改为 `DISABLED`。

### 输出

```java
public record ArchiveProductOutput(
        ProductCode productCode,
        ProductStatus status
) {}
```

成功时 `status` 固定为 `ARCHIVED`。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 按 `productCode` 查询当前 Product |
| 提交输出 | 将状态从 `OFF_SALE` 原子更新为 `ARCHIVED`，并递增版本 |

归档不物理删除 Product、SKU、库存或订单数据。

## 8. 放弃草稿

### 用户输入

```java
public record DiscardDraftProductInput(ProductCode productCode) {}
```

### 系统输入

```java
public record DiscardDraftProductSystemInput(
        Product currentProduct,
        boolean hasExternalReference
) {}
```

系统必须从 Repository 和外部引用检查器取得事实，不能相信客户端提交“没有引用”。

### 删除规则

- 商品当前必须为 `DRAFT`
- 商品不能存在任何外部业务引用
- 商品及其草稿 SKU、初始库存等从属数据在同一事务中删除
- 已分配的 `productCode` 和 `skuCode` 永不复用

`discardDraftProduct` 是明确的应用服务操作，不开放通用 Repository 删除接口给 Controller。

### 输出

```java
public record DiscardDraftProductOutput(
        ProductCode productCode,
        boolean discarded
) {}
```

成功时 `discarded` 固定为 `true`。若状态或引用检查不通过，则拒绝操作，不返回伪造的 `false` 成功结果。

### 副作用

| Phase | Side effect |
| --- | --- |
| 准备系统输入 | 查询当前 Product |
| 准备系统输入 | 查询活动、审核、搜索索引及异常历史数据等外部引用 |
| 提交输出 | 在同一事务中物理删除草稿 Product 及草稿从属数据 |
| 事务提交后 | 如有未复用的图片资源，提交异步资源清理任务 |

删除失败必须整体回滚。已经分配的业务编号不会因为删除成功而回收到编号池。

## 9. HTTP 接口

| Operation | Method and path |
| --- | --- |
| 创建商品 | `POST /api/admin/products` |
| 编辑基础资料 | `PUT /api/admin/products/{productCode}` |
| 首次上架 | `POST /api/admin/products/{productCode}/publish` |
| 下架 | `POST /api/admin/products/{productCode}/take-off-sale` |
| 重新上架 | `POST /api/admin/products/{productCode}/relist` |
| 归档 | `POST /api/admin/products/{productCode}/archive` |
| 放弃草稿 | `DELETE /api/admin/products/{productCode}` |

HTTP 层只把路径和请求正文转换为对应的用户输入。应用服务负责加载系统输入、执行事务并调用领域行为。状态接口不接受通用的 `status` 字段，因此不存在绕过状态机的：

```http
PATCH /api/admin/products/{productCode}
{ "status": "任意状态" }
```

## 10. 幂等与并发

幂等键属于应用层请求元数据，不是用户业务字段，也不进入 Product：

```http
Idempotency-Key: 7a1025df-1dad-42f0-94c8-8bc2d241ff65
```

创建操作使用幂等键避免重试产生重复商品。编辑和状态操作还应携带持久化版本进行乐观并发控制，防止两个后台操作人员用旧数据互相覆盖。

系统输入中的 `currentProduct` 是某一版本的权威状态。保存时若版本已经变化，本次操作应返回并发冲突，重新读取后由用户决定是否重试，不能静默覆盖。
